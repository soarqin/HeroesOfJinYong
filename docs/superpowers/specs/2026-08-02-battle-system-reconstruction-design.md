# 战斗系统重构与原版算法同步设计

## 1. 目标

本次工作重构现有战斗系统，并以 DOS 原版程序为依据同步战斗数值与 AI 行为。最终实现应满足以下目标：

- 将战斗规则、AI、寻路、回合调度、结算与 SDL 场景代码分离。
- 以可复现的逆向证据确认原版算法，不依赖经验值或现有实现推测。
- 复刻原版正常规则，修正确认属于缺陷的行为，并记录差异原因。
- 建立确定性测试体系，使数值、随机调用、AI 决策和完整战斗流程可回归验证。
- 保持现有存档结构、战斗入口和资源格式兼容。

## 2. 当前状态

现有战斗实现主要集中在以下位置：

- `src/scene/warfield.cc`：约 1,839 行，同时承担资源加载、地图状态、输入、渲染、动画、回合、寻路、AI、行动执行和战后结算。
- `src/scene/warfield.hh`：战斗瞬时状态与场景状态混合存放。
- `src/mem/action.cc`：包含战斗数值函数，也包含装备、物品、升级和队伍操作等非战斗职责。

项目当前没有自有测试目标。`cmake-build-release` 使用 Ninja 与 MinGW，可作为现有 Release 构建基线。`build` 与 `build64` 仍绑定旧路径和已不存在的 Visual Studio 2019，不作为本次验证入口，也不在本次工作中清理。

已发现的可疑实现包括：

- 敌方攻击时攻防双方的知识加成索引可能与阵营不匹配。
- AI 伤害预测没有复用完整防御计算。
- 上毒增量的返回符号可能与界面显示语义相反。
- 位于 `x == 0` 的死亡角色可能没有清理占位格。
- 自动使用物品前的移动目标可能采用了相反的距离比较方向。

这些项目仅作为逆向调查清单。在获得原版证据或可重复验证前，不直接视为缺陷修复。

## 3. 兼容策略

采用「算法复刻并修错」策略：

- 原版正常算法、整数截断、数据宽度、随机调用顺序和 AI 决策顺序作为兼容基准。
- 原版中可稳定复现但确认属于溢出、越界、符号错误或控制流错误的行为，在新实现中修复。
- 每项修复同时保留原版结果与修正结果测试，并在逆向文档中说明判断依据。
- 无法由静态分析确认的行为标记为待验证，不使用未经证明的近似实现代替结论。

## 4. 逆向范围与证据管理

### 4.1 已确认入口

初始分析对象如下：

| 文件 | 大小 | SHA-256 | 作用 |
| --- | ---: | --- | --- |
| `D:\DOS\LEGEND\Z.COM` | 413 字节 | `9DE4C8002F92759BD2771A4984FF02599121E6C66FED1EB0D7E905A327E2DAC1` | DOS 启动壳 |
| `D:\DOS\LEGEND\Z.DAT` | 343,217 字节 | `0034F836DEF2B287E62B0902F08CAB22B61B397F24D44D6038274F1750A007CE` | 主要 MZ 可执行文件 |

`Z.COM` 通过 DOS `int 21h`、`AX=4B00h` 执行 `Z.DAT`。idalib 已能无界面装载两者；`Z.DAT` 当前识别出 570 个函数，并可使用 Hex-Rays 反编译 16 位代码。

初始锚点包括：

- `Z.COM:0x10100`：入口。
- `Z.DAT:0x31DA0`：读取 `WAR.STA` 与 `WARFLD.IDX/GRP` 的战场资料加载函数。
- `Z.DAT:0x3859E`：读取 `FIGHT*.IDX/GRP` 并驱动战斗动画的函数。

地址仅对上述哈希对应的二进制有效。脚本发现哈希变化时必须停止应用旧地址表。

### 4.2 依赖闭包

逆向范围不限定为 `Z.COM` 和 `Z.DAT`。若控制流、进程启动、覆盖加载或数据解释继续涉及其他 EXE、COM、覆盖模块、驱动或包含可执行代码的数据文件，应继续追踪与战斗逻辑相关的依赖，并记录：

- 父级文件、调用位置和加载方式。
- 文件路径、大小与 SHA-256。
- 与战斗行为的关联。
- 已确认函数、数据结构与未确认分支。

原版目录保持只读。仓库不包含原版二进制，也不保存大段反编译文本。

### 4.3 仓库产物

- `tools/reverse/`：idalib 提取脚本、函数与交叉引用导出工具、哈希检查工具。
- `docs/reverse/`：二进制依赖图、函数地址表、数据结构说明、算法摘要、证据状态与差异记录。
- `tests/fixtures/battle/`：不包含原版资源的最小行为输入与期望结果。

每条行为结论使用稳定证据编号，并标记为以下状态之一：

- 「已确认」：由反编译、汇编和调用关系共同支持。
- 「推定」：证据方向一致，但仍存在未解析数据或分支。
- 「待运行验证」：静态分析无法排除多种行为。
- 「修正版差异」：原版行为确认存在缺陷，新实现有意不同。

## 5. 目标架构

### 5.1 战斗域

新增 `src/battle/`，实现不依赖 SDL、渲染器、窗口对象和帧更新的纯战斗域。建议组件如下：

- `BattleState`：角色、阵营、格子、回合队列、临时状态和胜负状态。
- `BattleCommand`：移动、技能、医疗、用毒、解毒、暗器、物品、休息和结束回合。
- `BattleEvent`：状态变化、移动步骤、伤害、状态变化、死亡、技能成长、回合结束和战斗结束。
- `BattleRules`：行动合法性、数值、范围、资源消耗与状态变化。
- `BattlePathfinder`：移动可达范围、攻击可达范围与路径重建。
- `BattleAi`：只读分析战斗快照，生成候选命令与评分。
- `BattleTurnOrder`：回合队列、速度排序、中毒处理和回合推进。
- `BattleRewards`：经验、升级、练功、制药和战后回写结果。
- `BattleRandom`：可注入随机源及随机调用跟踪。

### 5.2 场景适配层

`scene::Warfield` 保留以下职责：

- 加载战场贴图、动画和视觉资源。
- 收集键盘输入并转换为 `BattleCommand`。
- 将 `BattleEvent` 转换为移动、动画、音效、弹窗和数字显示。
- 在动画完成后通知引擎继续处理事件。
- 进入战斗时创建快照，战斗结束时提交允许持久化的结果。

`Warfield` 不再计算伤害、AI 评分、移动范围、回合顺序或奖励。

### 5.3 数据适配

现有 `CharacterData`、背包、技能、物品和战场资料通过适配器转换为战斗快照。战斗结束时只回写当前项目原本允许持久化的字段，包括生命、内力、中毒、受伤、体力、武功熟练度、经验和学习进度。

存档结构与序列化格式保持不变。战斗域不直接持有 `gSaveData`、`gBag` 或其他全局对象。

## 6. 命令与事件流程

标准处理流程为：

```text
BattleCommand
  -> 合法性检查
  -> BattleRules / BattlePathfinder / BattleRandom
  -> BattleState 状态变更
  -> BattleEvent[]
  -> Warfield 播放表现
  -> 动画完成回执
  -> 继续处理事件或进入下一命令
```

非法命令不得修改状态，并返回结构化原因。AI 生成的命令必须经过与玩家命令相同的验证。

## 7. 数值规则

每条数值规则记录以下信息：

- 输入字段和数据来源。
- 原版数据宽度与有符号性。
- 乘除顺序和整数除法截断位置。
- 上下限和资源不足时的处理。
- 随机调用次数、范围与顺序。
- 状态写入顺序和死亡后的短路条件。

覆盖范围包括：

- 实际攻击、防御与武功等级降级。
- 伤害波动、体力修正、受伤修正和距离衰减。
- 吸内力、上毒、医疗、解毒和暗器。
- 休息、回合中毒、双击和武功熟练度。
- 经验、等级提升、练功、物品制作和战后回写。

预测与实际结算共享同一套规则。预测模式只关闭随机波动和状态写入，不维护近似公式。

## 8. AI 设计

AI 按原版决策顺序分为以下阶段：

1. 处理生存优先级，包括体力、生命、中毒和内力阈值。
2. 枚举当前可用技能、物品和基础行动。
3. 枚举移动后可执行的合法目标。
4. 使用 `BattleRules` 计算候选收益，不复制数值公式。
5. 按原版规则比较预计伤害、击杀、多目标覆盖、距离、风险和资源消耗。
6. 按原版遍历顺序、平分规则和随机调用确定最终命令。
7. 将命令交给 `BattleEngine` 再次验证并执行。

AI 不直接修改角色、格子或场景状态。候选列表和评分明细可在调试构建中输出，便于对照原版。

## 9. 实施分期

### 9.1 子项目一：逆向与契约基线

- 建立 CTest 入口和纯逻辑测试目标。
- 建立确定性随机源与随机调用记录。
- 建立 idalib 脚本、哈希清单、函数地址表和证据编号。
- 建立回合、移动、数值、状态、AI 和结算行为清单。

### 9.2 子项目二：纯逻辑战斗核心

- 迁移状态、回合、合法性、寻路、范围、数值和结算。
- 使用适配器与现有 `Warfield` 并行运行。
- 逐项删除 `warfield.cc` 与 `mem/action.cc` 中已迁移的战斗规则。

### 9.3 子项目三：AI 与场景接入

- 迁移并同步 AI 决策流程。
- 将玩家输入和动画改为命令与事件驱动。
- 移除旧回调状态机和重复预测逻辑。
- 完成完整战斗模拟与场景集成验证。

每个子项目结束时，游戏仍应可构建、可运行，且已迁移部分由自动化测试保护。

## 10. 测试设计

使用 CMake `BUILD_TESTING` 与 CTest。测试目标只链接纯战斗域，不启动 SDL 窗口。

### 10.1 单元测试

- 数值规则：边界值、整数截断、固定随机序列、资源不足、死亡和状态叠加。
- 范围与寻路：阻挡、占位、地图边缘、最短路径、范围形状和平分顺序。
- AI：候选生成、候选排序、最终命令和随机消耗次数。
- 回合：速度排序、稳定排序、中毒、死亡清理和胜负判断。
- 结算：经验、升级、练功、制药和持久化回写。

### 10.2 契约测试

- 测试名称或元数据引用逆向证据编号。
- 已确认缺陷同时断言原版结果与修正结果。
- 需要原版资源的测试通过 `HOJY_ORIGINAL_DATA_DIR` 显式启用。
- 普通单元测试不依赖原版文件，避免把受版权保护的数据加入仓库。

### 10.3 集成测试

- 使用固定随机序列模拟完整多回合战斗。
- 断言命令、事件、状态摘要、胜负与奖励结果。
- 验证战斗加载、玩家行动、敌方行动、动画回执和战斗退出。
- 视觉表现保留短人工检查清单，逻辑结果必须自动化。

## 11. 错误处理

- 无效角色、技能、物品、地图坐标和资源引用不得造成越界访问。
- 非法命令返回原因且不修改状态。
- 资源加载错误包含文件名、战斗 ID 与使用位置。
- 逆向脚本发现文件缺失、哈希变化、加载器变化或地址失效时立即停止，不静默生成旧结论。
- 调试构建使用断言检查域内不变量；发布构建返回可诊断错误。

## 12. 完成标准

- `Warfield` 不再包含战斗数值、AI、寻路、回合排序或奖励算法。
- 所有已识别的原版战斗行为都有证据状态和自动化测试。
- 未确认行为保持显式标记，不作为兼容结论发布。
- 每项修复都有旧实现失败、新实现通过的回归测试，并记录与原版差异理由。
- Release 构建、全部 CTest 和确定性完整战斗模拟通过。
- 存档结构、原始资源格式和外部战斗入口保持兼容。
- 逆向工具可从入口重新生成地址与证据清单，并能继续追踪新增可执行依赖。

## 13. 风险与控制措施

- 16 位整数与随机调用顺序容易产生隐蔽差异：所有规则使用固定宽度与随机调用跟踪测试。
- 原版函数命名缺失：使用地址、调用关系、数据引用和行为证据共同标识，不依赖人工名称。
- 场景动画与逻辑互相等待：使用事件队列与动画回执，避免帧更新直接改变规则状态。
- 一次性替换难以回归：按三个子项目渐进迁移，每次只移除已有测试覆盖的旧逻辑。
- 原版可能启动其他模块：使用依赖闭包追踪，不把分析范围硬编码为两个文件。
